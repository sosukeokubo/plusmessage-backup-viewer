# 本文テキスト復元の試行錯誤

「+メッセージバックアップから本文を人間が読める形で復元する」というのが
このプロジェクトの中心的な目的。現状、まだこれは達成できていない。

以下、試した手法と得られた教訓を記録する。

## 現状 (2026-04-25 時点)

`scripts/analyze.ts` と `scripts/ui-probe.ts` を実 62MB ファイルに走らせた
結果、本文復元の現状は以下のとおり：

- ✅ ファイル構造の大枠 (TLV) は復元できている
- ✅ META, CONTACTS は正しくパースできる
- ✅ 画像 (JPEG + zlib-PNG) は抽出できている
- ✅ **SMS 受信箱の本文は 61 件すべて復元済み** (17 phone × 計 61 通、
  日本語・絵文字・改行を含む)
- ✅ **UI まで届いている**: `summary.inbox` → `composeThreadList` の
  仮想 thread → `buildInboxIndex` → `ThreadDetail` の `InboxBubble` の
  経路は実ファイルで検証済み（[findings-2026-04-25.md](./findings-2026-04-25.md)
  Section 10）
- ❌ MESSAGES (0x0005) 側 44 thread の本文は 1 件も復元できていない
  （8MB クラスの body が圧縮 or 暗号化されていると推測。65MB の 99.8% を
  占める領域）
- ❌ 44 実 thread の `peerPhone` は全件 undefined。SMS と +メッセージの
  会話を「同じ相手」として統合できていない
- ⚠️ **UX 面の二次問題**：SMS 会話がサイドバー後半に埋もれており
  (44 匿名 → 17 SMS の順)、表示名が `+819012340004` のままで連絡先名に
  解決できていない。「復元できていないように見える」原因はここ。

## 試行 1: ASCII 印字可能文字列の抽出

**手法:** スレッドボディ内の `0x20–0x7e` 連続 8 文字以上を抜き出す。

**結果:**
- UUID、URL、MIME type、SIP アドレス等のメタデータは取れる
- **日本語本文は 1 文字も取れない**（UTF-8 のリードバイト `0xE3` 等が run を
  切るため）
- 英語本文も取れない（ローカライズの結果、英語メッセージ自体がほぼ無い）

**結論:** 失敗。そもそも日本語が落ちる時点で用途に合わない。

## 試行 2: UTF-8 対応の run 抽出 (`extractTextRuns`)

**手法:** [src/parser/textRuns.ts](../src/parser/textRuns.ts) を実装し、ASCII
印字可能文字 + 妥当な UTF-8 マルチバイトシーケンスを 1 つの run として収集。
over-long エンコーディングとサロゲート範囲 U+D800–U+DFFF を拒否。

**結果:**
- 日本語を含むテキストは取れるようになった
- **ただしバイナリノイズも大量に混入する**。スレッドボディはバイナリデータが
  主体なので、偶然 UTF-8 として妥当なバイト列になる箇所が無数にある
- 例: `\[瑩jdAa`、`D<呈VE2`、`裾F*餔Vj籬jT熒n` のような「ASCII 記号の中に
  1 文字だけランダムな漢字」が大量発生

**結論:** 抽出器としては正しいが、**スレッドボディそのものから本文を復元
する方針に無理がある**ことが判明。スレッドボディは圧縮・暗号化・別
エンコーディング等で格納されているらしく、生 UTF-8 として拾えるのは
偶然バイト列が妥当な並びになったゴミでしかない。

## 試行 3: ノイズフィルタの強化

**手法:** [src/util/stringFilter.ts](../src/util/stringFilter.ts) に段階的に
フィルタを追加:

- URL / MIME / UUID / 全桁数字 / ALL_CAPS_CONSTANT の拒否
- ファイルパス、拡張子、SIP 行の拒否
- 日本語混入時は「バイナリ頻出記号 `<>[]{}\^|~` を含んだらゴミ」
- 日本語混入時は「連続する日本語コードポイントが 2 文字以上でなければゴミ」
- ASCII 単体時は「単語らしさ (whitespace 必須、意味のある綴り)」を要求

**結果:**
- バイナリノイズは激減
- **同時に本当の本文もほぼ全滅**。最新スクリーンショットでは 61 会話すべて
  「表示できるテキストはありません」「写真のみ」

**結論:** フィルタを強化する方向は間違いではないが、**そもそもスレッド
ボディ内に本文が生 UTF-8 では存在していない**可能性が高い。フィルタの強弱
で解決する問題ではない。

## 試行 4: SECTION_SETTINGS (0x0001) の構造化パース

**手法:** 16 進ダンプを目視して、SETTINGS セクションが実は SMS 受信箱
だと気づく。 [src/parser/inbox.ts](../src/parser/inbox.ts) でアンカー走査に
よる `InboxBucket[]` / `InboxMessage[]` を生成。

**結果 (2026-04-25 検証後):**
- 単体テスト上は動く（合成フィクスチャで 6 テスト緑）
- ✅ 実 62MB ファイルでも 17 バケット × 61 メッセージを復元、
  日本語・絵文字・改行すべて読める
- ✅ UI まで届いている (`composeThreadList` で仮想 thread として注入、
  `ThreadDetail` の `InboxBubble` がレンダリング)
- ⚠️ ただし UI 上は「会話 45〜61」の位置に埋もれていて、表示名も国際表記
  電話番号のまま。**データは取れているのに見えていない**状態

**結論:** **試行 4 の方針はそのまま正解**。残課題は復元アルゴリズム
ではなく UI の見せ方 (表示順、表示名) と、別系統 (MESSAGES) 本文の
未着手領域に移る。

## 教訓

1. **ノイズフィルタで解決しようとするのをやめる。** 「読めるテキスト」
   を機械的に判定するフィルタは、本文とバイナリノイズのギリギリの所で
   必ず誤判定が出る。**本文が入っている位置と形式を特定してから**直接
   読み出すのが正しい

2. **「目視で読めるから UTF-8 で入っている」は罠。** SETTINGS セクションは
   生 UTF-8 で入っていたので運良く読めたが、MESSAGES セクションの方は圧縮
   されているかもしれない。hexdump の印字可能文字だけを見て全体像を判断
   しない

3. **仮説は小さく検証する。** 「この section は inbox だろう」→ 長さ
   接頭辞がどこにあるか → アンカーは何バイトか → 1 レコードは何バイトで
   終わるか、と段階を踏んで検証するべき。いきなり全体のパーサを書いて
   テストをパスさせても、実ファイルで動かなかった場合にどこが違うのか
   特定できない

4. **実ファイルでの観測ログを常に残す。** 「実ファイルで parseInbox が
   何件返すか」「アンカーが何個見つかるか」をコンソールに出せば、現在の
   実装のどこで詰まっているかが 5 分で分かる。これをやらずにテストだけで
   進めたのが今回の遠回りの原因

## 次に取るべきアプローチ (2026-04-25 改訂版)

実ファイル検証 (試行 4 ✅) を経て、優先順位は次のとおり：

### A-1. 「復元できた感」を UI に出す（コスト極小・即効）

SMS 復元は完了しているが、UI 上は埋もれて見えない。次の 2 つだけで
体感が大きく変わる：

- `formatPhone` を `+81` プレフィックス対応にし、国際表記を
  `0xx-xxxx-xxxx` にダウングレード表示する
- `composeThreadList` で **仮想 (SMS) thread をリスト先頭に並べる**
  か、少なくとも「メッセージが取れている会話」を上位にソートする

これだけで「62MB のファイルから 61 通の SMS が読めた」がユーザにとって
可視化される。所要 30 分以内、リスクほぼゼロ。

### A-2. 連絡先の名前抽出を強化（中・要調査）

`deriveContactName` は実ファイル 85 件の連絡先で **全件 `undefined`** を
返している。本当に名前データが入っていないのか、抽出ロジックが取り損ねて
いるのか未確定。先に調査スクリプトで CONTACTS フィールドを目視する。

### B. 44 実 thread の `peerPhone` 解決（中・本筋）

実 thread の peer 紐付けが解ければ、SMS の virtual thread と統合できて
サイドバーが綺麗になる。手がかり：

- thread body 内の長さ接頭辞付き `+`-phone を全部スキャンし、最頻出を
  peer 候補とする
- CONTACTS の 85 件と、何らかの id (thread_id?) で対応するか検証

これが解けると、SMS と +メッセージが同一相手で統合され、44 + 17 が
本当の会話相手数（おそらく 30〜40 人程度）に集約される。

### C. MESSAGES 本文の格納方式特定（深掘り・本丸）

65MB の 99.8% を占める MESSAGES (0x0005) の本文がどこにどう入っているか。
attachment が zlib-PNG で圧縮されているので、本文も同様の層で圧縮されて
いる仮説が現状最有力 ([open-questions.md](./open-questions.md) Q3/Q6)。

検証手順：

1. 実機で「確実に送受信した特定フレーズ」を thread body 内で **生 UTF-8
   バイト grep** → ヒットすれば生格納、ヒットしなければ圧縮 or 暗号化
2. ヒットしなければ thread body 全域で `78 9c` / `78 01` / `78 da`
   (zlib ヘッダ) を列挙し、attachment 以外の zlib ストリームを探す
3. それでも見つからなければ Protobuf / MessagePack / 独自 TLV を疑う

C は時間が読めない。A-1 → A-2 → B → C の順で着手するのが、各段階で
何かしら成果が積み上がる流れ。
