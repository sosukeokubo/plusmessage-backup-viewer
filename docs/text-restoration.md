# 本文テキスト復元の試行錯誤

「+メッセージバックアップから本文を人間が読める形で復元する」というのが
このプロジェクトの中心的な目的。**2026-04-26 時点で、SMS と +メッセージの
両方について、送受信を区別したうえで UI まで復元する所までほぼ達成した**
([findings-2026-04-26.md](./findings-2026-04-26.md))。

以下、ここに至るまでに試した手法と得られた教訓を記録する。

## 現状 (2026-04-26 時点)

`scripts/analyze.ts` / `scripts/ui-probe.ts` / `scripts/grep-bytes.ts` /
`scripts/scan-zlib.ts` を実 62MB ファイルに走らせ、`InboxBubble` を direction
別に表示するよう改修した結果、本文復元の現状は以下のとおり：

- ✅ ファイル構造の大枠 (TLV) は復元できている
- ✅ META, CONTACTS は正しくパースできる
- ✅ 画像 (JPEG + zlib-PNG + zlib-GIF) は抽出できている
- ✅ **SMS 受信箱の本文は 61 件すべて復元済み** (17 phone × 計 61 通、
  日本語・絵文字・改行を含む)
- ✅ **+メッセージ送信本文も復元済み** (実機 65MB ファイルで 5 件、
  日本語・絵文字・改行・送信タイムスタンプを含む)。アンカーを
  受信 (`07…05`) と送信 (`06…04`) の 2 種に対応させたことによる。
  詳細: [findings-2026-04-26.md](./findings-2026-04-26.md)
- ✅ **送受信方向 (`direction`) の付与** — 旧実装は常に `'unknown'` を
  返していたが、アンカー先頭バイトで `'incoming' | 'outgoing'` を判別する
  ようになった。
- ✅ **UI で送受信が区別表示される** — `InboxBubble` を direction で
  分岐させ、送信は右寄せ + accent カラー、受信は左寄せ + accent-weak。
  時系列ソートも `ThreadDetail` 側で `timestamp.ms` 昇順に実施済み。
  ブラウザで最終確認済み。
- ❌ 44 実 thread の `peerPhone` は全件 undefined。SMS / +メッセージの
  本文は SETTINGS から取れているが、MESSAGES 側の thread (画像メイン) と
  「同じ相手」として統合できていない (Q4 / B タスク)
- ⚠️ **UX 面の二次問題**：SMS / +メッセージ会話がサイドバー後半に埋もれており
  (44 匿名 → 17 inbox の順)、表示名が `+819012340004` のままで連絡先名に
  解決できていない。これは A-1 / A-2 タスク。

## 試行 1: ASCII 印字可能文字列の抽出

**手法:** スレッドボディ内の `0x20–0x7e` 連続 8 文字以上を抜き出す。

**結果:**

- UUID、URL、MIME type、SIP アドレス等のメタデータは取れる
- **日本語本文は 1 文字も取れない**（UTF-8 のリードバイト `0xE3` 等が run を
  切るため）
- 英語本文も取れない（ローカライズの結果、英語メッセージ自体がほぼ無い）

**結論:** 失敗。そもそも日本語が落ちる時点で用途に合わない。

## 試行 2: UTF-8 対応の run 抽出 (`extractTextRuns`)

**手法:** [src/parser/textRuns.ts](../src/parser/textRuns.ts) を実装し、ASCII
印字可能文字 + 妥当な UTF-8 マルチバイトシーケンスを 1 つの run として収集。
over-long エンコーディングとサロゲート範囲 U+D800–U+DFFF を拒否。

**結果:**

- 日本語を含むテキストは取れるようになった
- **ただしバイナリノイズも大量に混入する**。スレッドボディはバイナリデータが
  主体なので、偶然 UTF-8 として妥当なバイト列になる箇所が無数にある
- 例: `\[瑩jdAa`、`D<呈VE2`、`裾F*餔Vj籬jT熒n` のような「ASCII 記号の中に
  1 文字だけランダムな漢字」が大量発生

**結論:** 抽出器としては正しいが、**スレッドボディそのものから本文を復元
する方針に無理がある**ことが判明。スレッドボディは圧縮・暗号化・別
エンコーディング等で格納されているらしく、生 UTF-8 として拾えるのは
偶然バイト列が妥当な並びになったゴミでしかない。

## 試行 3: ノイズフィルタの強化

**手法:** [src/util/stringFilter.ts](../src/util/stringFilter.ts) に段階的に
フィルタを追加:

- URL / MIME / UUID / 全桁数字 / ALL_CAPS_CONSTANT の拒否
- ファイルパス、拡張子、SIP 行の拒否
- 日本語混入時は「バイナリ頻出記号 `<>[]{}\^|~` を含んだらゴミ」
- 日本語混入時は「連続する日本語コードポイントが 2 文字以上でなければゴミ」
- ASCII 単体時は「単語らしさ (whitespace 必須、意味のある綴り)」を要求

**結果:**

- バイナリノイズは激減
- **同時に本当の本文もほぼ全滅**。最新スクリーンショットでは 61 会話すべて
  「表示できるテキストはありません」「写真のみ」

**結論:** フィルタを強化する方向は間違いではないが、**そもそもスレッド
ボディ内に本文が生 UTF-8 では存在していない**可能性が高い。フィルタの強弱
で解決する問題ではない。

## 試行 4: SECTION_SETTINGS (0x0001) の構造化パース

**手法:** 16 進ダンプを目視して、SETTINGS セクションが実は SMS 受信箱
だと気づく。 [src/parser/inbox.ts](../src/parser/inbox.ts) でアンカー走査に
よる `InboxBucket[]` / `InboxMessage[]` を生成。

**結果 (2026-04-25 検証後):**

- 単体テスト上は動く（合成フィクスチャで 6 テスト緑）
- ✅ 実 62MB ファイルでも 17 バケット × 61 メッセージを復元、
  日本語・絵文字・改行すべて読める
- ✅ UI まで届いている (`composeThreadList` で仮想 thread として注入、
  `ThreadDetail` の `InboxBubble` がレンダリング)
- ⚠️ ただし UI 上は「会話 45〜61」の位置に埋もれていて、表示名も国際表記
  電話番号のまま。**データは取れているのに見えていない**状態

**結論:** **試行 4 の方針はそのまま正解**。残課題は復元アルゴリズム
ではなく UI の見せ方 (表示順、表示名) と、別系統 (MESSAGES) 本文の
未着手領域に移る。
(※ この時点での「別系統 = MESSAGES」という想定は試行 5 で覆る。
本文は MESSAGES ではなく SETTINGS 側に集約されていた。)

## 教訓

1. **ノイズフィルタで解決しようとするのをやめる。** 「読めるテキスト」
   を機械的に判定するフィルタは、本文とバイナリノイズのギリギリの所で
   必ず誤判定が出る。**本文が入っている位置と形式を特定してから**直接
   読み出すのが正しい

2. **「目視で読めるから UTF-8 で入っている」は罠。** SETTINGS セクションは
   生 UTF-8 で入っていたので運良く読めたが、MESSAGES セクションの方は圧縮
   されているかもしれない。hexdump の印字可能文字だけを見て全体像を判断
   しない

3. **仮説は小さく検証する。** 「この section は inbox だろう」→ 長さ
   接頭辞がどこにあるか → アンカーは何バイトか → 1 レコードは何バイトで
   終わるか、と段階を踏んで検証するべき。いきなり全体のパーサを書いて
   テストをパスさせても、実ファイルで動かなかった場合にどこが違うのか
   特定できない

4. **実ファイルでの観測ログを常に残す。** 「実ファイルで parseInbox が
   何件返すか」「アンカーが何個見つかるか」をコンソールに出せば、現在の
   実装のどこで詰まっているかが 5 分で分かる。これをやらずにテストだけで
   進めたのが今回の遠回りの原因

## 試行 5: 送信アンカーの存在に気づく (2026-04-26)

**手法:** ユーザー提供の +メッセージ送信スクリーンショットから 4 件の固有
フレーズを抜き、`grep-bytes.ts --utf8 "<フレーズ>"` でファイル全域を検索。
ヒット位置の前後 256 B を hexdump して構造を読み解いた。

**結果:**

- 4 件すべて **SETTINGS 範囲** にヒット (offset 0x540a–0x5779)
- MESSAGES 範囲では 0 件
- `scan-zlib.ts` で 44 thread の zlib stream を全列挙したが、本文を含む
  stream は皆無 (見つかったのは画像 — PNG / GIF89a のみ)
- ヒット位置の手前に **`06 00 00 00 01 00 00 00 00 00 00 00 04 00 00 00 00 00 00 00`**
  という 20 byte 列があり、その後ろの構造は受信 SMS とまったく同じ
  (timestamp → textLen → text → mimeLen → "text/plain" → uuidLen → uuid → …)

**結論:** **SETTINGS は SMS だけでなく送信側 +メッセージも含んでいた**。
parseInbox が拾えていなかったのは、受信用アンカー (`07…05`) しか走査していなかったから。
**送信用アンカー (`06…04`) を `findAllAnchors` に追加するだけで、+メッセージ
本文が直ちに復元できる**。
詳細: [findings-2026-04-26.md](./findings-2026-04-26.md)。
これでようやく、本プロジェクトの中心的な目的に到達する見通しが立った。

## 試行 6: 送信アンカーの実装と UI への反映 (2026-04-26)

**手法:** 試行 5 の発見に基づき、`src/parser/inbox.ts` に送信アンカー
`ANCHOR_OUTGOING` (`06…04`) を追加。`findAllAnchors` を `AnchorHit[]`
(`{ offset, direction }`) を返すよう変更し、`readMessage` が直接
`direction` を `InboxMessage` に詰める形に整理。あわせて
`src/ui/ThreadDetail.tsx` の `InboxBubble` を direction で右寄せ／左寄せ

- 配色分岐するように改修。

**結果:**

- 実 65MB ファイルで **66 メッセージ復元** (受信 61 + 送信 5)。送信 5 件は
  ユーザー提供スクショ #2 の 4 件 + 2023 年最古の 1 件と完全一致
- `direction` が `'incoming' | 'outgoing'` で正しく付与される
- `pnpm dev` 上のブラウザで「会話 37 件 (in=32, out=5)」のスレッドを開くと、
  送信メッセージは右寄せ青背景、受信は左寄せ薄青背景でレンダリングされる
- 既存テスト含めて 72 件すべて緑、`tsc -b --noEmit` 通過

**結論:** **本プロジェクトの中心目的「+メッセージバックアップから本文を
人間が読める形で復元する」に到達**。残るは UX 仕上げ (A-1/A-2) と
スレッド統合 (B) で、いずれも「読める所までは届いている」状態。

## 次に取るべきアプローチ (2026-04-26 試行 6 後)

「文字の復元」自体は ✅ 達成済み。残課題を価値順に並べると次のとおり:

### A-1. 「復元できた感」を UI に出す（コスト極小・即効）

復元は完了しているが、サイドバー上は依然として 44 実 thread が先頭、
17 inbox virtual thread がその後に並ぶ。次の 2 つで体感が大きく変わる：

- `formatPhone` を `+81` プレフィックス対応にし、国際表記を
  `0xx-xxxx-xxxx` にダウングレード表示する
- `composeThreadList` で **inbox 由来の virtual thread をリスト先頭** か、
  少なくとも「メッセージが取れている会話」を上位にソートする

所要 30 分以内、リスクほぼゼロ。

### A-2. 連絡先の名前抽出を強化（中・要調査）

`deriveContactName` は実ファイル 85 件の連絡先で **全件 `undefined`** を
返している。本当に名前データが入っていないのか、抽出ロジックが取り損ねて
いるのか未確定。先に調査スクリプトで CONTACTS フィールドを目視する。

### B. 44 実 thread の `peerPhone` 解決（中・本筋）

実 thread の peer 紐付けが解ければ、SMS / +メッセージ inbox の virtual
thread と統合できてサイドバーが綺麗になる。手がかり：

- thread body 内の長さ接頭辞付き `+`-phone を全部スキャンし、最頻出を
  peer 候補とする
- CONTACTS の 85 件と、何らかの id (thread_id?) で対応するか検証

これが解けると、44 実 thread と 17 inbox bucket が同一相手で統合され、
本当の会話相手数（おそらく 30〜40 人程度）に集約される。

### C (旧). MESSAGES 本文の格納方式特定 — ✅ 否定済み

旧仮説「MESSAGES (0x0005) に +メッセージ本文が圧縮or暗号化で格納」は
2026-04-26 の試行 5 で否定された。本文は SETTINGS 側に集約されており、
MESSAGES は thread メタデータと画像添付の格納先と推定。
詳細: [findings-2026-04-26.md](./findings-2026-04-26.md) Section 3。

### ✅ 副次タスク. attachments.ts の GIF 対応 (2026-09-02 完了)

`scan-zlib.ts` の検証で、PNG signature しか見ていない `attachments.ts` が
GIF89a 添付を取りこぼしていることが判明していた。シグネチャテーブル化して
PNG/GIF87a/GIF89a に対応した結果、実ファイルの添付は 32 → 44 件に増え、
「画像なし」に見えていた 12 会話すべてに画像 (+メッセージのスタンプ) が
表示されるようになった。
詳細: [findings-2026-09-02.md](./findings-2026-09-02.md)。
