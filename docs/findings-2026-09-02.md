# 2026-09-02 検証ログ: zlib-GIF 添付の検出対応

[findings-2026-04-26.md](./findings-2026-04-26.md) Section 4 で積み残していた
「`attachments.ts` が GIF 添付を取りこぼしている」を解消した記録。

対象ファイル: `PlusMessage.backup` (65,159,882 B)

## 1. 原因の特定

当初「zlib ヘッダの prefilter が GIF stream を候補から外している」という
仮説が出たが、**これは誤り**。thread 2 の body を直接走査して確認した：

```
thread 2: prefilter通過=42  inflate成功=1  PNGシグネチャ=0  GIFシグネチャ=1
現行 scanPngZlib が記録した attachment 数 = 0
```

GIF の zlib stream は `CMF=0x78` かつ `(CMF<<8|FLG) % 31 === 0` の prefilter を
**通過しており**、`tryInflate` も**成功して 315,082 B を展開できていた**。
にもかかわらず attachment が 0 件だったのは、その直後の
`startsWithPngSignature(res.result)` が弾いていたため。

これは構造的に当然で、**zlib ヘッダは中身の形式について一切情報を持たない**。
PNG か GIF かは展開してからでないと判別できないので、形式の判定は prefilter
ではなく inflate 後に置くしかない。`scripts/scan-zlib.ts` が同じ prefilter を
使いながら GIF を 12 件「UNKNOWN」として列挙できていたことも裏付けになる。

## 2. 実データの分布

`scan-zlib.ts` の全 44 スレッド走査：

| 項目 | 件数 |
|---|---|
| zlib stream 総数 | 57 |
| 既存 attachment (PNG) として記録済み | 18 |
| inflate 結果が `GIF89a` で始まる stream | **12** |
| 残り (8〜30 B の偽陽性) | 27 |

GIF を持つのは thread **2, 3, 5, 6, 7, 8, 10, 12, 26, 27, 33, 36** の 12 件。
findings-2026-04-26 では「26 / 27 / 33 / 36 など」と書いていたが、正確には
12 スレッドで、**その全てが対応前は `att=0`（添付ゼロ）判定**だった。
つまり UI 上で完全に「画像なし会話」に見えていた。

`GIF87a` は 1 件も存在しない（実データは全て `GIF89a`）。生（非圧縮）の GIF も
ゼロ。したがって対応範囲は **zlib 包みの GIF のみ**とし、生 GIF のスキャンは
検証できないため実装しない。

## 3. 実装

[src/parser/attachments.ts](../src/parser/attachments.ts)

- `startsWithPngSignature` を廃し、`ZLIB_IMAGE_SIGNATURES` テーブル
  (PNG / GIF87a / GIF89a) と `matchImageSignature` に置換
- `scanPngZlib` → **`scanZlibImages`** にリネーム（PNG 限定でなくなったため）
- `AttachmentRef.encoding` の `'zlib-png'` → **`'zlib'`** にリネーム。
  Worker 側の処理は inflate するだけで画像形式に依存せず、形式は
  `contentType` が持つ。形式を足すたびに encoding が増えるのを防ぐ
- `AttachmentRef.kind` / `Attachment.kind` に `'image/gif'` を追加

GIF87a と GIF89a は共通接頭辞 `GIF8` ではなく 6 バイト完全一致で判定する
（`GIF8xx` な別物を通さないため）。

[src/ui/WelcomeScreen.tsx](../src/ui/WelcomeScreen.tsx) の説明文
「写真（JPEG/PNG）」も実態に合わせて「写真（JPEG/PNG/GIF）」に修正。

## 4. 検証結果

### 4.1 実ファイルでのパース

```
parse: 762ms  threads=44  添付ありthread=44
kind別: { 'image/png': 18, 'image/gif': 12, 'image/jpeg': 14 }
```

12 件すべてが `encoding=zlib` で検出され、Section 2 の予測スレッドと完全一致。
**添付ありスレッドは 32 → 44** になった（12 スレッドが「画像なし」から回復）。

### 4.2 パース時間への影響

同一プロセスで 3 回連続パースした warm な値の比較：

| | 添付数 | 実行時間 |
|---|---|---|
| 修正前 (HEAD) | 32 | 776 / 602 / 611 ms |
| 修正後 | 44 | 863 / 598 / 578 ms |

**有意差なし**。prefilter も inflate も元から全候補に対して実行されており、
今回増えたのは展開後の先頭 6 バイト比較だけなので、これは予測どおり。

### 4.3 ブラウザでの確認 (playwright-cli)

`pnpm dev` に実ファイルを投入して確認：

| 会話 | blob type | サイズ | マジック | 表示サイズ | 備考 |
|---|---|---|---|---|---|
| 会話 2 | `image/gif` | 308 KB | `GIF89a` | 500×500 | |
| 会話 3 | `image/gif` | 355 KB | `GIF89a` | 500×500 | スクショ取得 |
| 会話 26 | `image/gif` | 480 KB | `GIF89a` | 500×500 | `NETSCAPE2.0` = アニメ GIF |

Blob をページ内で `fetch` して先頭バイトを直接読み、`GIF89a` であることと
`naturalWidth/Height` が 500×500 にデコードされていることを確認済み
（500 = GIF ヘッダの `f4 01 f4 01`）。コンソールエラーは 0 件。

画面上では会話 3 に「おはよう」の文字入りキャラクターイラストが表示された。
実会話が写るためスクリーンショットはリポジトリに残していない。

### 4.4 新規発見: GIF の正体は +メッセージのスタンプ

会話 3 の GIF は「おはよう」の文字入りキャラクターイラストで、
これは **+メッセージのスタンプ**。12 件が全て 500×500 で揃っていること、
一部がアニメーションであることもスタンプ仕様と整合する。

つまり「写真のみ」と表示されていた会話の実態は「スタンプのみ」の可能性が
高い。UI の文言を将来見直す余地がある（P2）。

## 5. テスト

[test/attachments.test.ts](../test/attachments.test.ts) を 12 → 16 件に拡張：

- zlib-wrapped GIF89a / GIF87a の検出（`it.each`）
- `GIF85a` のような偽の `GIF8` 接頭辞を弾くこと
- PNG と GIF が混在する連続 stream を両方拾うこと
- 既存の PNG ケースを `encoding: 'zlib'` に追随

`pnpm test` 75 件パス、`pnpm typecheck` エラーなし。

## 6. 使用スクリプト

```
pnpm tsx scripts/scan-zlib.ts ./PlusMessage.backup
```

原因特定と検証に使った一時スクリプト（prefilter 通過数のカウント、
kind 別集計、before/after ベンチ）はコミットしていない。再現手順は
上記の数値と併せて本ドキュメントに残す。
