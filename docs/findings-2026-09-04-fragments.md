# 2026-09-04 「テキスト断片」は添付のバイト列だった — 通常表示からの撤去

UI には「取り出せたテキスト断片」という枠があり、`解読できていない領域から
拾えた文字列` と説明していた。SETTINGS を構造解読した結果、この説明が
成り立たなくなっていたので、実測して確かめた上で通常表示から外した。

使用スクリプト: 一時プローブ（`parseBackup` → `thread.strings` を集計）。
以下はすべて実ファイル 1 件（65MB）に対する観測値。

## 1. 観測 — 8,199 件中、フィルタを通るのは 1 件

`sections.ts` は THREAD body から `extractTextRuns` で UTF-8 として成立する
バイト列を拾い、UI 側は `filterMessageStrings` で本文らしいものだけを残して
表示していた。

```
raw fragments 8199 → filterMessageStrings 通過後: 1
通過した唯一の 1 件: "Jnyiht X"
```

内訳は CJK を含むもの 234 件、ASCII/ラテンのみ 7,965 件。CJK 側も中身は
本文ではない。形だけ示すと次のようなもので、単独の漢字が ASCII 記号の間に
挟まっているだけである。

```
臁;dW¹#Gޖk
{GL#ZT岊x
%领%)~׾Iϴ
```

`strings=500` という上限に張り付いている thread が複数ある。

## 2. 原因 — 走査対象が画像そのもの

THREAD (0x0006) レコード 1 件は**メディア 1 件**であり、body は添付の
バイト列そのものである（`findings-2026-09-02-peers.md`）。8MB の JPEG を
バイトスキャンすれば、偶然 UTF-8 として妥当な並びが数百件見つかる。

つまり断片が拾っていたのは「解読できていないテキスト」ではなく、
**解読済みの画像バイナリ**だった。

この枠は SETTINGS を構造解読する前、本文に触れる唯一の手段だった頃の名残で
ある。現在は本文 112 通・メディア 44 件が正規の経路で取れているので、
役目を終えている。

## 3. 対応

通常表示から外し、`?debug=1` のときだけ見えるようにした。見出しも
「取り出せたテキスト断片」から「body から拾ったバイト列」に改め、
`添付の中身であって本文ではない` と添えた。

- `src/util/stringFilter.ts` と `test/stringFilter.test.ts` を削除。
  debug 表示は元々フィルタを通していない (`debug ? thread.strings : …`) ため、
  通常表示を消すとフィルタの呼び出し元が無くなる
- サイドバーの `断片N` バッジと、プレビューの断片フォールバックを削除
- WelcomeScreen から「解読できていない領域から拾えた文字列は…」の一文を削除。
  事実と異なる記述だった
- `extractTextRuns` と `thread.strings` は**残した**。別条件のバックアップで
  未解読領域に本文が入っていた場合に気づく手段が無くなるため

## 4. ブラウザ確認 (playwright-cli, localhost:5173)

- 通常表示: 断片パネル無し、`断片N` バッジ 0 件、詳細ペインのヘッダは
  `メッセージ N 件 · 写真 N 枚`、コンソールエラー 0 件
- `?debug=1`: 「body から拾ったバイト列」パネルが件数付きで表示される
