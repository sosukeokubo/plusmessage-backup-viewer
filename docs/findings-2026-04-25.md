## 結論（先に書く）

1. **`parseInbox` は実ファイルで想定通りに動いている。** 17 バケット・
   61 メッセージを完全な日本語 UTF-8 で復元できる。
2. **SETTINGS 解析は完了扱いでよい。** MESSAGE_ANCHOR 検出数 (61) が
   メッセージ件数と一致、取りこぼし 0 を確認。
3. **次のボトルネックは THREADS 側。** MESSAGES セクション (0x0005) が
   ファイルの 99.8% を占め、44 スレッドの `peerPhone` はすべて未解決
   (`peer=-`)。本文復元の未解決分はこちら。
4. **UI 側の問題も顕在化。** `backup.inbox` に 61 件の SMS 本文が載って
   いるにもかかわらず、UI には出ていない。サイドバーの「会話 1…61」は
   44 スレッド + 17 inbox バケット = 61 のラベルで、中身の紐付けが
   外れていると思われる。

したがって「本文復元」のロードマップは当初想定と大きく変わる：

- ✅ SMS 本文 (SETTINGS, 61 件) — **すでに取れている**。あとは UI に出すだけ
- ❌ +メッセージ本文 (MESSAGES, 44 スレッド) — 未着手のまま、真の未解決領域

## 7. 観測から導かれる次の手

優先度順：

### A (優先・即着手) — SMS 61 件を UI に出す

- `backup.inbox` は正しく埋まっている
- しかし UI のスレッド一覧には反映されていない
- `buildInboxIndex` ないし `ThreadSummary` と `InboxBucket` の紐付け（phone
  を key とした join）で詰まっていると推測
- **具体的な次作業**：
  1. UI のストア/インデックス構築コード（`src/util/contactResolver.ts`
     あたり）を読み、`peerPhone` key で `InboxBucket` が引けるか確認
  2. 44 スレッドに紐付かない 17 バケットを独立した「SMS 受信箱」
     セクションとしてサイドバーに並べる（当初計画 [text-restoration.md]
     の提案 3 の実装）
- これが出来るだけで「文字の復元」はユーザ目線では成功体験に変わる

### B (次に着手) — THREAD の peerPhone 解決

- 44 スレッド中 0 件が peer 解決できていない
- 手がかり：thread body 内の長さ接頭辞付き `+`-phone を探す、または
  CONTACTS (85 件) と thread インデックスの対応を当たる（Q4）
- CONTACTS が 85 件、THREAD が 44 件なので 1:1 のインデックス対応では
  ない。thread body 内を走査するのが筋

### C (深掘り) — MESSAGES 本文の格納方式

- これが解ければ +メッセージ本文が復元できる
- 実機で「確実に送受信したフレーズ」を byte grep、ダメなら body 内に
  zlib ヘッダ (`78 9c` 等) があるか全走査（Q3/Q6）
- 当初は「圧縮か暗号化か」の二択だったが、attachment の zlib-PNG と同じ
  層で本文も圧縮されている可能性が高い

## 8. 補足：スレッド 500 件の string cap

string 抽出数が `500` で頭打ちになっているスレッドが 10 本以上ある。
[src/parser/textRuns.ts](../src/parser/textRuns.ts) 側に上限があると思われ、
本文が混ざっていた場合に取りこぼしている可能性がある。ただし「本文が
生 UTF-8 で入っている前提が崩れた」（[text-restoration.md:42-50]) ので、
ここを広げるより MESSAGES 本文の格納方式特定 (C) が先。

## 10. 追補 (2026-04-25 後半): UI 配線は実は壊れていない

セクション 4 で「UI に inbox が出ていない／中身の紐付けが外れている」と
書いたが、これは **誤った推測** だった。
[scripts/ui-probe.ts](../scripts/ui-probe.ts) で `composeThreadList` +
`buildInboxIndex` + `resolveThreadContact` を実ファイルに対して走らせた結果、
データパイプラインは想定通り動いていることを確認した。

### 確定事実

| 観測項目                             | 値                        |
| ------------------------------------ | ------------------------- |
| `summary.threads` (実スレッド)       | 44                        |
| `summary.inbox` バケット             | 17                        |
| inbox メッセージ総数                 | 61                        |
| `composeThreadList` 結果             | 61 (real 44 + virtual 17) |
| `inboxIndex` キー数                  | 17                        |
| inbox messages を持つ composed entry | 17 (= virtual 全件)       |
| inbox メッセージが届いていない phone | **0 件**                  |

つまり：

- 17 バケット × 61 メッセージは `summary.inbox` → `composeThreadList` の
  仮想 thread → `buildInboxIndex` → 詳細ペインまで **全部届いている**
- `ThreadDetail.tsx` の `InboxBubble` も実装済み。
  クリックすれば SMS 本文が表示される

### では何が「復元できていないように見える」のか

サイドバー上で起きている実際の問題は別の 2 つ：

**問題 X1: SMS 会話がリスト後半に埋もれている**

- `composeThreadList` は `[...threads, ...virtual]` の順で連結
- 結果、サイドバー上から 44 件は「会話 1〜44」のフォールバック、
  **45 件目以降にやっと SMS 会話が現れる**
- ユーザは普通サイドバー先頭から見るので「全部空っぽに見える」体験

**問題 X2: 表示名が `+819012340004` のベタ書き**

- `formatPhone` は 10/11 桁日本国内表記しか整形しない。
  国際表記 (`+81…`、12 桁) は素通し
- 連絡先 85 件はあるが、`deriveContactName` で `name` が全件 `undefined`
  なので、`resolveThreadContact` が表示名にフォールバックできない
- 結果、せっかく phone が紐付いていても「+819012340001」のような無味な
  文字列が出るだけ

### 上記 X1/X2 が起きていることの直接証拠

`scripts/ui-probe.ts` の出力（一部抜粋）：

```
[ 43] R  msgs=  0  name="会話 44"                         peer=-
[ 44] V  msgs=  1  name="+819012340004"                   peer=+819012340004
...
[ 56] V  msgs= 32  name="+819012340001"                   peer=+819012340001
[ 60] V  msgs= 13  name="+819012340002"                   peer=+819012340002
```

- `R` = 実 thread (`peerPhone` 全件 undefined → 「会話 N」)
- `V` = inbox 由来の仮想 thread (`peerPhone` 紐付き、メッセージ届いている)
- 32 通会話 (`+819012340001`、ありがとうございました…) は **57 番目** にある

### この発見でロードマップが変わる

当初 Section 7 で「A: SMS 61 件を UI に出す」が最優先と書いたが、
**A は既に達成済み**。
本物のロードマップは：

- **A-1 (コスト極小・即効)**: `formatPhone` を `+81` プレフィックス対応にし、
  `composeThreadList` で SMS 会話を先頭に並べ替える。これだけで
  「復元できた感」が体感的に大きく改善する
- **A-2 (中)**: `deriveContactName` の改善。85 件の連絡先のうち本当に名前が
  入っているものを見つけて UI に出す（あるいは、入っていないことを確定
  させて A-2 をスキップする）
- **B**: 44 実 thread の `peerPhone` 解決。これが解けると real と virtual が
  マージされ、サイドバーに重複が無くなる
- **C**: MESSAGES 本文の格納方式特定。本丸（写真しか出ない 44 会話の本文）
