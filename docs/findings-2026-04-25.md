# 実ファイル検証ログ (2026-04-25)

`scripts/analyze.ts` を実 `PlusMessage.backup` (65,159,882 B / 62.14 MiB) に
対して実行した結果。[open-questions.md](./open-questions.md) の Q1
「`parseInbox` は実ファイルで何件取れているか」に実測で答える。

## 使用ツール

- `pnpm tsx scripts/analyze.ts ./PlusMessage.backup`
- 対象：作業ディレクトリ直下の `PlusMessage.backup`
- パーサバージョン：`0.1.0`

## 結論（先に書く）

1. **`parseInbox` は実ファイルで想定通りに動いている。** 17 バケット・
   61 メッセージを完全な日本語 UTF-8 で復元できる。
2. **SETTINGS 解析は完了扱いでよい。** MESSAGE_ANCHOR 検出数 (61) が
   メッセージ件数と一致、取りこぼし 0 を確認。
3. **次のボトルネックは THREADS 側。** MESSAGES セクション (0x0005) が
   ファイルの 99.8% を占め、44 スレッドの `peerPhone` はすべて未解決
   (`peer=-`)。本文復元の未解決分はこちら。
4. **UI 側の問題も顕在化。** `backup.inbox` に 61 件の SMS 本文が載って
   いるにもかかわらず、UI には出ていない。サイドバーの「会話 1…61」は
   44 スレッド + 17 inbox バケット = 61 のラベルで、中身の紐付けが
   外れていると思われる。

したがって「本文復元」のロードマップは当初想定と大きく変わる：

- ✅ SMS 本文 (SETTINGS, 61 件) — **すでに取れている**。あとは UI に出すだけ
- ❌ +メッセージ本文 (MESSAGES, 44 スレッド) — 未着手のまま、真の未解決領域

## 1. ファイル / セクション構成

| section | type | offset | length |
|---------|------|--------|--------|
| META | 0x000b | 0x0000007e | 121 |
| CONTACTS | 0x000d | 0x000000f7 | 9,919 |
| SETTINGS (inbox) | 0x0001 | 0x000027b6 | 114,719 |
| MESSAGES | 0x0005 | 0x0001e7d5 | **65,034,974** |
| END | 0x0008 | 0x03e242b3 | 14 |

- `bytesConsumed == fileSize` — EOF まで綺麗に読み切っている
- MESSAGES (65.0 MB) が全体の 99.8%、SETTINGS は 0.18% のみ
- `unknownSections` は 0 件

## 6. MESSAGES / THREADS

- スレッド数：**44**
- すべての THREAD で `peerPhone` が未解決 (`peer=-`)
- body サイズは 32 KB ～ **8.3 MB** まで幅広い
- 大きいスレッドは `strings` が 500 で頭打ち（抽出器の上限に到達）
- `flag=0x00` と `flag=0x01` が混在（分布：0x00 が 16 本、0x01 が 28 本）
- 大半に attachment が 1 つ（JPEG/PNG）

|---------:|---------:|-----|-----:|-----:|

| 23 | 8,326,928 | 0x00 | 1 | 500 (cap) |

| 41 | 7,586,103 | 0x00 | 1 | 500 (cap) |
| 24 | 7,185,795 | 0x00 | 1 | 500 (cap) |

→ これらが +メッセージの実コンテンツ。本文がどう格納されているかが
残る最大の謎。

## 7. 観測から導かれる次の手

優先度順：

### A (優先・即着手) — SMS 61 件を UI に出す

- `backup.inbox` は正しく埋まっている
- しかし UI のスレッド一覧には反映されていない
- `buildInboxIndex` ないし `ThreadSummary` と `InboxBucket` の紐付け（phone
  を key とした join）で詰まっていると推測
- **具体的な次作業**：
  1. UI のストア/インデックス構築コード（`src/util/contactResolver.ts`
     あたり）を読み、`peerPhone` key で `InboxBucket` が引けるか確認
  2. 44 スレッドに紐付かない 17 バケットを独立した「SMS 受信箱」
     セクションとしてサイドバーに並べる（当初計画 [text-restoration.md]
     の提案 3 の実装）
- これが出来るだけで「文字の復元」はユーザ目線では成功体験に変わる

### B (次に着手) — THREAD の peerPhone 解決

- 44 スレッド中 0 件が peer 解決できていない
- 手がかり：thread body 内の長さ接頭辞付き `+`-phone を探す、または
  CONTACTS (85 件) と thread インデックスの対応を当たる（Q4）
- CONTACTS が 85 件、THREAD が 44 件なので 1:1 のインデックス対応では
  ない。thread body 内を走査するのが筋

### C (深掘り) — MESSAGES 本文の格納方式

- これが解ければ +メッセージ本文が復元できる
- 実機で「確実に送受信したフレーズ」を byte grep、ダメなら body 内に
  zlib ヘッダ (`78 9c` 等) があるか全走査（Q3/Q6）
- 当初は「圧縮か暗号化か」の二択だったが、attachment の zlib-PNG と同じ
  層で本文も圧縮されている可能性が高い

## 8. 補足：スレッド 500 件の string cap

string 抽出数が `500` で頭打ちになっているスレッドが 10 本以上ある。
[src/parser/textRuns.ts](../src/parser/textRuns.ts) 側に上限があると思われ、
本文が混ざっていた場合に取りこぼしている可能性がある。ただし「本文が
生 UTF-8 で入っている前提が崩れた」（[text-restoration.md:42-50]) ので、
ここを広げるより MESSAGES 本文の格納方式特定 (C) が先。
