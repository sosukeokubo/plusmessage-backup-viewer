# 実ファイル検証ログ (2026-04-26)

`scripts/grep-bytes.ts` と `scripts/scan-zlib.ts` を実 `PlusMessage.backup`
(65,159,882 B) に対して走らせ、[open-questions.md](./open-questions.md) の
**Q3 (本文の所在)** と **Q6 (+メッセージ本文の所在)** に答えた。

[text-restoration.md](./text-restoration.md) で挙げた 3 つの仮説のうち:

- **仮説 A (生 UTF-8 で格納)** — ✅ 確定。ただし格納場所は `MESSAGES` ではなく `SETTINGS`
- **仮説 B (zlib 圧縮)** — 否定。本文を含む zlib stream は見つからず
- **仮説 C (Protobuf / 暗号化)** — 検証不要 (A で説明がつく)

## 結論（先に書く）

1. **+メッセージ本文 (送信側) は `SETTINGS` セクション内に、SMS と同じ生 UTF-8 形式で格納されている**。
   parseInbox が現在拾えていなかったのは、**送信メッセージのアンカーが受信のものと違う**ため。
2. アンカーの差は固定の 2 バイトのみ。受信は `07 ... 05`、送信は `06 ... 04`:

   | 種別 | 20 バイトアンカー |
   |-----|-----|
   | 受信 (SMS / +メッセージ受信) | `07 00 00 00  01 00 00 00  00 00 00 00  05 00 00 00  00 00 00 00` |
   | 送信 (+メッセージ送信)        | `06 00 00 00  01 00 00 00  00 00 00 00  04 00 00 00  00 00 00 00` |

3. アンカー以降のレコード構造は完全に同一 (タイムスタンプ → textLen → text → mimeLen → mime → uuidLen → uuid → sipLen → sip → trailer)。
   違うのは MIME 文字列の値だけ:
   - 受信: `text/plain;charset=utf-8` (24 B)
   - 送信: `text/plain` (10 B、末尾スペース含むかは要確認)
4. **MESSAGES (0x0005) は本文を持たない**。65 MB の 99.8 % を占める 44 thread の役割は今のところ「画像添付ファイルとスレッドメタデータの格納先」と考えるのが妥当。
   `scan-zlib.ts` で 44 thread を全走査したが、attachment 範囲外の zlib stream はゴミ (8B 程度の偽陽性) しか見つからなかった。
5. **副次的発見**: PlusMessage の添付には **GIF も含まれる**。attachments.ts は PNG signature しか見ておらず、`thread 26 / 27 / 33 / 36` などの zlib stream は inflate すると `GIF89a` で始まる画像になる。これらは現在の attachment スキャナで取りこぼしている。

## 1. 仮説 A の検証

ユーザー提供の実機スクリーンショット (花子さんとのスレッド、+メッセージで送信した 4 件) からフレーズを抜き出して `grep-bytes.ts` で検索した。

| # | 送信日付 | 検索フレーズ | ヒット位置 | 範囲 |
|--:|---------|------------|----------|-----|
| 1 | 2024-01-16 | `Why` (= `Why？\n連絡待ってますよ🍀`) | `0x00005779` | SETTINGS +12217 |
| 2 | 2024-02-28 | `今年もよろしくお` | `0x00005663` | SETTINGS +11939 |
| 3 | 2025-03-01 | `70回目の記念日になる` | `0x0000551e` | SETTINGS +11614 |
| 4 | 2026-02-28 | `あいかわらず` | `0x0000540a` | SETTINGS +11338 |

すべて **SETTINGS 範囲 (0x27b6 – 0x1e7d5)** にヒット。**MESSAGES 範囲 (0x1e7d5 – 0x3e242b3) では 0 件**。

> ⚠️ 当初は `--range 0x1e7d5:0x3e242b3` で MESSAGES 限定で検索して 0 件だったため
> 仮説 A は否定されたかに見えた。範囲指定を外したら全件 SETTINGS に出てきて、
> 「本文は MESSAGES にある」という前提自体が誤りだったことが判明。

## 2. アンカーの全件確認

```
pnpm tsx scripts/grep-bytes.ts ./PlusMessage.backup --hex "06 00 00 00 01 00 00 00 00 00 00 00 04 00 00 00 00 00 00 00"
```

→ **5 ヒット**、すべて SETTINGS 範囲内 (offset `0x539a` / `0x54f0` / `0x5623` / `0x5759` / `0x18724`)。
スクショで確認済みの送信 4 件 + α (画像送信ではないテキスト送信が他にもう 1 件あるはず)。

## 3. 仮説 B の否定

`scripts/scan-zlib.ts ./PlusMessage.backup --limit 100` を 44 thread に対して実行:

```
threads scanned:              44
zlib hits total:              57
matched to attachment record: 18    (= 既知 PNG attachment と一致)
UNKNOWN (not an attachment):  39
```

UNKNOWN 39 件の内訳:

- 大半は in=8〜30 B / out=0〜30 B のごく短い偽陽性 (CMF/FLG % 31 がたまたま通って `inflateSync` が早期に成功するケース)
- 数件 (`thread 26, 27, 33, 36` 等) は in≈500 KB の本物の zlib stream で、inflate すると **`GIF89a` で始まる**。これは GIF 画像であり、本文ではない

→ **本文テキストを含む zlib stream は 1 件も見つからなかった**。仮説 B は不要。

## 4. 副次的発見: GIF 添付

`attachments.ts` は `scanPngZlib` で PNG signature を要求しているため、上記の GIF stream を attachment として記録していない。本来は thread 26 / 27 / 33 / 36 などにも添付があるはずで、UI で「画像なし会話」に見えていた一部はこのせい。

別タスクとして `attachments.ts` に GIF 検出を追加するのが望ましい。

## 6. パーサ実装と再検証 (同日中に実施)

調査結果を反映するパーサ改修を同日に実施した。

### 6.1 実装内容

- [src/parser/inbox.ts](../src/parser/inbox.ts):
  `MESSAGE_ANCHOR` を `ANCHOR_INCOMING` (= 既存 `07…05`) と `ANCHOR_OUTGOING` (= `06…04`) の 2 種に分割。
  後方互換のため `MESSAGE_ANCHOR` は `ANCHOR_INCOMING` のエイリアスとして残置。
- `findAllAnchors` の戻り値を `number[]` から `AnchorHit[] = { offset, direction }[]` に変更し、
  両アンカーを offset 昇順でマージ。
- `readMessage` を anchor 引数 (型 `AnchorHit`) で受け、`InboxMessage.direction` に
  そのまま `'incoming' | 'outgoing'` を入れる (旧実装は常に `'unknown'`)。
- [test/inbox.test.ts](../test/inbox.test.ts) に送信アンカー専用テスト 1 件と、
  受信＋送信が同一バケットに混在するケースのテスト 1 件を追加 (計 +2、合計 8 件 緑)。
- [scripts/analyze.ts](../scripts/analyze.ts) を direction 別の集計付き出力に更新。

### 6.5 残課題 (今回スコープ外)

  バケット 0 に正しく紐付いているが、構造的には興味深い。後で hexdump で
  領域境界を確認するとよい (P2 マイナー)。
- A-1 (`formatPhone` の +81 対応 / SMS 会話を先頭ソート)、
  A-2 (`deriveContactName` の改善)、
  B (44 実 thread の `peerPhone` 解決) は引き続き未着手。
